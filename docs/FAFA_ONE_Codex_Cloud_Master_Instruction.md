## 1. 产品目标和导航

FAFA ONE 是一个**统一控制面板**，核心是「VPN/代理订阅聚合 + Codex 多账户工作台 + 自有服务器管理 + 位置预设中心 + 用户权限后台」。用户不需要知道 SSH/订阅转换的实现细节即可完成常用操作。全站不添加 eSIM、QQ/微信登录，不擅自增加其他 AI 服务入口。

- 用户端主导航：`仪表盘`、`节点订阅`、`Codex`、`服务器`、`位置中心`、`我的账户`。
- 管理端主导航：`概览`、`用户/邀请`、`节点源/订阅分配`、`服务器授权`、`AI 连接状态`、`任务队列`、`安全审计`、`系统设置/备份`。
- PC：左侧可折叠导航 + 顶部搜索、通知、主题、个人资料；卡片式信息仪表盘。手机：固定底部五项导航，详情页面单列排版、Bottom Sheet 和大点击区域。
- 数据层级必须分清：**平台管理员可用的共享资源**、**用户个人资源**、**用户自己的订阅与密钥**，前后端均强制隔离。
- 20 人为首期上限：在系统配置中可调整；默认仅受邀 Google 账号可激活，管理员可发邀请、禁用、撤销会话、分配角色和节点额度。

## 2. UI/UX 视觉规范：以两张参考效果图为唯一主风格

实现高保真 **FAFA ONE 玻璃液态控制台**，不是普通 Bootstrap 管理模板。界面须比视觉稿更可用：视觉稿中的数值仅是占位内容，实际产品禁用假状态。

- 风格关键词：Premium / Minimal / Liquid Glass / Calm / Precise；浅色主题以浅蓝、云白、雾紫玻璃质感为主，深色主题以午夜蓝、石墨黑、低亮紫边缘为主。避免强烈廉价霓虹或过度背景模糊。
- 推荐 Design Tokens：主色 `#635BFF`，次色 `#4D91FF`，强调 `#9A63FF`，成功 `#20B67A`，告警 `#E8A33A`，危险 `#E4576B`；颜色需在浅/深主题经可读性校验。玻璃卡可用 rgba 表面与 12–20px blur，但表单、表格、长文必须有足够不透明度与对比度。
- 字体：系统字体优先，中文使用兼容的无衬线回退。8px 间距体系，卡片 16–24px 内边距，圆角 16–22px，阴影柔和，所有 icon 一致。
- Motion：120–240ms 的位移/淡入/悬停状态，支持 `prefers-reduced-motion`，不能为动效牺牲响应速度。
- 仪表盘展示：在线节点、服务器总量、已用席位/20、流量**只有可核实数据才显示**；VPN 大卡、Codex 大卡、服务器卡、位置中心卡、权限卡及快捷操作区。
- 手机屏宽 320/375/390/430px；概览指标真正自适应 2×2 或横滑但禁止页面整体横向滚动；较大卡片采用单列。底部导航兼容安全区域、刘海、键盘弹起和 Safari 地址栏变化。
- 细节：Skeleton、Toast、空状态、连接错误、重试、复制成功、ConfirmDialog、命令面板（Ctrl/Cmd+K）、焦点指示、统一状态 Badge、键盘可操作、中文辅助描述。
- 页面必须拆成独立路由与可复用组件，不能将截图整体做成一张背景图片。

## 3. 技术架构（前端/后台/服务真正独立）

推荐一个偏稳健、适合 20 人的 TypeScript monorepo：

```text
apps/
  web/          # 用户端 React/Next.js，独立构建部署
  admin/        # 管理端 React/Next.js，独立构建部署
  api/          # Fastify + Zod/OpenAPI，独立后端，提供 HTTPS/WS
  worker/       # 后台刷新/测速/队列任务；可与 api 开发同机部署
packages/
  ui/           # shadcn/ui、Tailwind、Lucide、设计 token、公共组件
  db/           # PostgreSQL schema、migrations、seed
  auth/         # Google 登录和登录态
  subscription/ # 安全解析、标准化、去重、规则、导出
  shared/       # 类型、验证器、状态枚举、权限、脱敏工具
infra/
  docker/       # Dockerfile、compose.dev/production
  reverse-proxy/# Caddy/Nginx 样例
  scripts/      # 开发初始化、备份和恢复脚本
docs/           # 架构、部署、威胁模型、审计、接口、验收报告
reference_images/
```

可调整框架但必须说明理由；不引入过度复杂的 Kubernetes。数据层 PostgreSQL，ORM 选 Drizzle 或 Prisma 并保持迁移管理；Redis 仅当任务队列确需时引入，不要为展示而增加成本。开发阶段 `pnpm dev` + `docker compose up -d` 应可跑通；严格区分 `DEMO_MODE=true` 与真实模式。生成 `.env.example`，不得提交真实密钥。

建议域名采用配置方式：`panel.<用户域名>`（web）、`admin.<用户域名>`（admin）、`api.<用户域名>`（api），**不要把效果图里的示例域名当成用户实际拥有的域名**。TLS、CORS、Cookie Domain 等按生产/本地环境分别设置。

## 4. Google 登录、邀请和 20 人多租户隔离

- 唯一登录入口为 Google Identity Services / OIDC；使用经过验证的服务端授权流程和官方库；验证 ID Token 签名、iss、aud、exp、nonce/state/CSRF，使用 Google `sub` 作为不变用户唯一标识，不以邮箱作为身份主键。
- 管理员首次绑定通过受控的 `BOOTSTRAP_ADMIN_GOOGLE_SUB` / 一次性初始化脚本，禁止前端任意自封管理员；注册受邀校验；根据产品选择是否要求 verified email。
- 角色：Owner、Admin、Member、Viewer；RBAC 在 API/数据库查询上强制执行，不仅是菜单隐藏。Viewer 不得创建订阅、开终端或操作账户。
- 每个用户拥有各自的第三方订阅源、已获分配的共享节点、订阅令牌、Codex 凭据、服务器列表、连接任务、审计记录。未经授权访问他人对象返回不暴露资源存在性的错误（404 或等价）并留安全审计。
- 会话：Secure/HttpOnly/SameSite Cookie、会话撤销/设备管理、闲置超时、登录异常限流、敏感操作再认证、管理端额外二次认证准备。
- 用户界面提供「我的数据导出/删除请求」，制定最小化数据保留期。不得宣传「完全不存储个人数据」，因为账户标识、订阅与服务器配置确有必要存储。

## 5. 核心模块 A：VPN 节点与订阅聚合

### 5.1 源与模型

- `NodeSource`：`OWNED_NODE`（管理员/用户拥有的节点）与 `REMOTE_SUBSCRIPTION`（用户获得授权的第三方订阅 URL）；两类源同时存在，可以通过节点分组和可见性权限向用户分配。
- 支持源名称、链接/协议、国家标签、供应商、更新时间、有效期、最近一次成功同步、是否启用、拥有者、可见范围、错误信息和配额配置。
- 第三方订阅链接只能使用有权使用和聚合的资源；不公开上游专用认证信息，不擅自共享他人订阅内容。
- 合理解析 Clash/Mihomo YAML、sing-box JSON、常见 URI/Base64 列表与用户实际需要的 VLESS/VMess/Trojan/SS/Hysteria2 等。**必须有格式单元测试**，不能声称所有协议兼容而未验证。
- 统一标准化 schema：协议、host、port、凭据引用、传输/TLS/配置、国家/地区标签、源 ID、用户可见性。去重以规范化完整节点身份计算，避免 host/port 相同但密钥不同的节点被误删。

### 5.2 独立订阅与动态刷新

- 用户注册激活后默认分配**唯一、可轮换、可撤销**订阅 Token，供 Shadowrocket（小火箭）、Mihomo、sing-box、v2rayN 等客户端使用；以客户端经过测试的真实兼容格式输出，支持手动选择目标格式。
- UI：统一订阅 / 自有节点 / 第三方节点 Tab，国家筛选、搜索、节点数、流量/失效日期、启停、刷新、复制链接/二维码、订阅详情、同步错误、历史。
- 支持订阅源定时刷新、条件请求（ETag/Last-Modified）、退避重试、失败保留最后成功版本、管理员手动刷新、失败告警、变更 diff；后台 worker 执行，不在用户 HTTP 请求中长时间阻塞。
- 管理员可控制每位用户节点开放、可用源、订阅生效/失效、下载限频、可配置额度；来自第三方的流量消耗若无可靠计量接口显示 `数据不可用`，不能生成假剩余流量。
- 节点测速仅在真实探测时显示时间戳、探测位置、测量类型、失败状态；不要使用随机毫秒数。
- 订阅 URL 属于**敏感凭据**：生成高熵 Token、不得在普通日志打印、允许轮换撤销、避免被搜索引擎索引、限制重定向和缓存泄露。

### 5.3 订阅抓取安全

对可由用户控制的 URL 防 SSRF：只接受 https（有明确例外需配置）、限制端口/大小/超时/重定向、DNS 解析和连接时双重检查、禁止 loopback、link-local、云 metadata、私网和保留地址（除受控可信代理/服务代理特殊路径），避免 DNS rebinding；严格解析 YAML / JSON 不执行任意表达式，防 zip bomb/大文件和日志泄漏。

## 6. 核心模块 B：Codex 多账户工作台

### 6.1 账户模型与真实接入原则

- 每用户可创建多个账户条目，如 `主用`、`开发`、`测试`，显示昵称、接入类型、创建时间、验证时间、连接状态、凭据有效性、当前选中账户；切换不能影响其他人的会话。
- **已可实现的方式**：用户自行提供受支持的 OpenAI API Key，后端加密保存，按选择的 API 凭据执行允许的 API/SDK 请求；显示明确计费方式，不把 API Key 模式伪称为「使用 ChatGPT Plus 订阅额度」。
- **需要服务商授权的方式**：第三方托管面板内使用 ChatGPT 订阅授权的 Sign in with ChatGPT 集成，须取得所需资格与支持。未获批准时按钮标记 `暂未开放` 并说明原因，不能通过收集聊天 Cookies、会话 Token、CLI auth.json、设备码或劫持登录回调绕过授权。
- 官方 Codex Cloud 是单独产品环境；如无已公开获准且可用的 API，不得伪装内嵌控制其云任务。可提供「打开官方 Codex Cloud」外链与项目/仓库关联说明；未来留 Provider Adapter 接口。

### 6.2 工作台功能

- 左侧/顶部账户切换器、账户连接状态、最近会话、任务列表、工作区选择器、任务状态（排队/进行中/等待批准/完成/失败/取消/超时）。
- 支持本面板可合规执行的 API 助手交互、流式消息（SSE 或 WS）、错误重试、取消、会话恢复、关联 GitHub 工作目录；服务端对速率、令牌预算和任务并发实行限制。
- 服务器远程执行由独立的「SSH 授权工作区」承担；Codex 生成的 shell 命令默认仅作建议，**执行需要拥有者显式确认**；写文件、重启服务、部署等危险动作额外二次审批并审计。
- 不得跨账户共享 `~/.codex`、`~/.config`、密钥文件或 Docker home 目录；不同用户/账户/工作区相互隔离。所有密钥/日志脱敏。
- 当没有 OpenAI API Key 时，显示真正的「未连接/待配置」，但用户仍能浏览完整 UI 和添加账户向导。

## 7. 核心模块 C：我的服务器 / SSH 远程终端

- 用户在「添加服务器」页单独填写：备注名称、IPv4/IPv6/域名、SSH 端口（默认 22）、登录用户名、认证方式（推荐 SSH Key，兼容密码）、所在地区标签、分组、环境标签。
- SSH 私钥和密码绝不放在浏览器 localStorage 或数据库明文字段；使用服务端 envelope encryption、版本化 key ID、可轮换主密钥；前端保存后仅展示 `已配置`。不得把凭据放入 URL、日志、错误栈。
- 服务器连接流程：连接验证、主机指纹首次确认/持久固定、断线重连、超时、权限拒绝、凭据失效、连接审计。禁止自动接受改变的 SSH host key。
- 真正的 Web 终端可基于 `@xterm/xterm` + 服务端 SSH2 + 授权 WS 通道构建，服务端按登录用户和目标服务器做权限校验，限制会话数量/闲置超时，保证移动端输入法和复制粘贴可用。
- 可配置敏感命令显式确认、只读终端模式、禁止 Viewer 使用终端。非管理员只可使用本人服务器或被明确授权的服务器。
- 防止服务器管理模块沦为内网扫描器：任何 IP/域名必须由用户有权管理，采用明确授权目标列表、严格出口策略。内网目标推荐通过受控 agent/Tailscale 类安全连接方式接入，而非允许匿名任意探测私网。
- 服务器页面：我的服务器列表、在线/离线/未知状态、最近成功连接、添加/编辑/删除/测试、SSH 终端、快捷命令模板（需要授权）、连接日志。状态来自真实检测。

## 8. 核心模块 D：位置中心 / 小火箭联动（技术边界不可造假）

界面保留视觉稿风格，但**将能力明确拆成**：

1. `IP 出口地区`：在用户确实拥有的代理节点中选择出口国家/地区，生成/更新合适的订阅策略；此项影响代理流量的出口 IP，不是 GPS。
2. `地图位置预设`：在网页地图上搜索城市、保存经纬度/地点并显示预览，这只是平台保存的坐标配置，不会修改 iPhone 的系统定位。
3. `系统 GPS 定位`：单纯网页、Shadowrocket 代理规则或手机重启，不能被认定为可改变 iOS 系统 Core Location。若未来有合法、技术上可验证的设备侧方案，再单独做能力检测和明确授权的设备桥接；在支持前用 `暂不支持`/`待验证`，不可写「重启后生效」。

针对 iOS 26.3 进行兼容性测试，不得仅依据版本号推导有 GPS 修改能力。小火箭页可以提供已验证的订阅导入和规则下载，不应声称控制苹果系统定位。地图服务需处理地图供应商 API Key、调用配额、隐私、错误回退。

## 9. 后台管理、权限、运营

- 管理端与用户端使用不同域名/独立构建，不共用管理页面 bundle；共享 API 必须在服务端验证每个请求的权限。
- 用户管理：邀请、Google 绑定状态、账号启停、角色、席位额度、最后登录、邀请撤销与过期、数据导出/删除。
- 节点管理：源清单、分组/标签/国家、权限分配、订阅刷新队列、成功/失败、订阅 token 轮换、客户端版本兼容矩阵、上游授权合规记录。
- Codex：各账户仅展示非敏感连接摘要，管理员不可查看其他用户 API Key 明文；检测任务失败、提供匿名化健康摘要和排障建议。
- 服务器：拥有者、授权范围、连接审计、异常/频繁失败告警，不允许管理员直接提取任意用户存储的秘密。
- 系统：API health/readiness、任务队列、失败重试、环境配置校验、维护模式、备份/恢复、运行指标、日志/审计、异常速率限制。
- 管理首页统计真实用户数和真实在线检测值；无监控数据时显示 `未接入`/`暂无数据`。允许演示环境数据但所有卡片须清楚标 `演示数据`。

## 10. 数据设计（最低限度）

至少有以下实体及迁移、索引、外键、拥有权/授权模型：

`users`, `google_identities`, `invitations`, `sessions`, `roles`, `permissions`, `user_role_grants`, `audit_events`, `node_sources`, `nodes`, `node_groups`, `node_group_grants`, `subscription_profiles`, `subscription_tokens`, `subscription_sync_runs`, `node_health_checks`, `traffic_usage_samples`, `ai_accounts`, `ai_sessions`, `ai_tasks`, `server_connections`, `server_access_grants`, `ssh_sessions`, `location_presets`, `background_jobs`, `settings`。

- 统一用 UUID 主键、创建/修改时间、软删除/撤销时间（适用时）、owner ID、保密字段 encryption metadata。业务查询受权限过滤。
- 业务状态使用有限状态机枚举，不用随机字符串。API 错误统一码+中文信息+ correlation ID，不泄漏敏感堆栈。
- 对高敏感操作写 append-only 审计记录；审计事件不得存密码、API Key、订阅 URL 明文、终端输出秘密。

## 11. 工程质量与安全要求

- CI：pnpm install frozen lockfile、lint、format check、typecheck、unit test、integration test、build、Playwright smoke、依赖漏洞扫描、secret scan；PR 才合并。
- 端到端：Google 假认证只在测试环境，邀请/超额/禁用、RBAC、跨用户读取 404、订阅合并转换与撤销、上游 SSRF、Codex 账户切换与未授权状态、SSH 无效 host key 和未授权终端、位置能力说明、手机布局、断网及空状态。
- 真实 iPhone Safari 的最终设备验收由人执行并留报告；自动 WebKit 模拟不能冒充真机验收。其他覆盖 Chrome/Firefox/WebKit、Android Chrome。
- 核心页面响应式检查：320、375、390、430、768、1024、1440、1920px，浅/深色、文字放大、键盘焦点、触摸、Safe Area、横向溢出、滚动冲突。
- 性能目标（上线前需在真实部署复测）：Lighthouse Performance 目标 ≥90、Accessibility ≥95，LCP ≤2.5s、CLS ≤0.1、INP ≤200ms；实际检测数据与环境一并报告。
- 安全：HTTPS/TLS、CSP、XSS/CSRF、防注入、精确 CORS、鉴权中间件、速率限制、密钥加密与轮换、日志脱敏、依赖锁版本、SSR F 防护、上传/解析大小限制、SSRF 和认证单测、最小权限、数据库备份加密。
- 不要把远程用户输入直接拼接进 shell；采用参数化执行或安全命令模板。所有高风险操作需明确的用户确认。

## 12. 无服务器阶段的可运行方案

当前不需要购买或绑定生产 VPS。必须完成：

1. 本地与 Codex 云开发容器中的可运行基础系统，依赖文档、`.env.example`、非敏感 seed。
2. `docker compose` 让 Web、Admin、API、PostgreSQL 和必要 Worker 启动，具备 health/readiness；没有 Google 凭据时提供开发专用 mock 登录（只在 `NODE_ENV=development` 且显式开关下开放），生产环境强制禁用。
3. 演示模式：国家节点样例、Codex 账户样例、服务器样例、用户席位样例**全部清晰标注为演示**，默认不得调用外部 SSH/代理/AI 服务。
4. 生产部署准备：多域名 Caddy/Nginx 反代、TLS 证书、迁移/初始化、容器最小权限、secret 配置、自动备份/恢复脚本、README 操作手册。
5. 服务器规格建议仅写在 `docs/DEPLOYMENT.md`，须说明根据并发 SSH 终端、后台任务和流量测算扩容；实际 VPN 出口节点不应与本面板 API 混为一台必需主机。
6. 不要自行购买服务器、注册 OAuth 凭据、建立收费账户、改变 DNS 或部署到旧生产环境。

## 14. 交付标准与执行顺序（不要只完成阶段 1）

**阶段 0：审计**：列出现有仓库情况、最小迁移路线、风险、执行清单与 screenshots 差距。  
**阶段 1：设计 + 工程底座**：monorepo、Design Tokens、玻璃主题、Web/Admin 独立路由、空态/演示态、登录框架、DB。  
**阶段 2：节点完整闭环**：订阅源 CRUD、解析、权限、聚合、导出、token 轮换、刷新任务、测试。  
**阶段 3：Google 登录 + 20 人授权 + Admin**：邀请/席位/用户管理/安全审计。  
**阶段 4：Codex**：多 API 账户、真实受支持 API 对接、账户切换、状态、任务、官方 ChatGPT 登录待授权门控。  
**阶段 5：服务器**：SSH 凭据存储、校验、连接终端、授权/审计、移动操作。  
**阶段 6：位置中心**：IP 出口、地图预设、小火箭订阅指引、系统 GPS 的不支持边界。  
**阶段 7：完整验收**：视觉对照、E2E、性能/安全、部署文档、回归检查、PR。

至少形成：

- 完整可运行的源码、锁文件、DB migrations、测试、Docker 开发/生产样例；
- `README.md`（新手 5 分钟本地启动）、`docs/ARCHITECTURE.md`、`docs/PRODUCT_SPEC.md`、`docs/SECURITY.md`、`docs/DEPLOYMENT.md`、`docs/OPEN_SOURCE_ATTRIBUTION.md`、`docs/ACCEPTANCE_REPORT.md`；
- 真正的桌面与移动端实现、对照视觉截图，以及管理员和普通用户的关键操作路径；
